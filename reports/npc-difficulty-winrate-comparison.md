# NPC全4難易度の勝率比較

基準は Web 版 `main` の `1570b799e08235ba6c941a8921dc89fe8d45ce78`。正式実装済みの「やさしい・標準・強い・最強」を、正式ゲームエンジンで **31,104試合**比較した。6対戦×9デッキ条件×576試合。以下の総合表は各試合を両者の成績に一度ずつ数えるため、各難易度15,552試合、全行の試合数合計は62,208。

## 結論

- **順番は「最強 > 強い > 標準 > やさしい」**。単純集計・6分類均等・ランダムの同一構成／独立構成のいずれでも同じだった。各デッキ条件内でも、6対戦のいずれにも上位難易度の負け越しはなかった。ただし、個別のデッキ構成すべてに一般化するものではない。
- **最強は強いに有意に勝ち越した。** 5,184試合で最強2,543勝・1,927敗・714引き分け。勝率49.05%に対して得点率55.94%（95%区間54.77〜57.11%）で、互角の50%を上回った。ランダム2条件では524勝・414敗・214引き分け、得点率54.77%（52.45〜57.10%）。ランダム独立だけでは最強の得点率53.65%（50.20〜57.09%）と差は小さかった。全9条件で勝ち越したが、条件ごとの区間は多重比較を補正していない。
- **やさしいは初心者向けに設けた弱さの目安に沿う。** 対標準の全条件で28.78%（27.39〜30.18%）、ランダム同一で25.69%、ランダム独立で34.72%。2枚提出43.47%、与ダメージ12.80／試合で、標準の70.61%、15.18／試合を下回る。NPC同士の成績から初心者本人の勝率や楽しさは推定できない。
- **引き分けの多い対戦では勝率だけだと差を読み違えやすい。** 強い vs 最強の速攻同一は引分26.39%。最強は勝率41.15%でも、187敗に対して237勝し、得点率54.34%だった。また、独立に組んだランダム戦では、やさしいの対標準勝率が同一構成より9.03ポイント高かった。両難易度に両方のデッキを割り当てた条件での差で、特定の組成が有利だったとは断定できない。
- 最強は強いより襲撃成功率が1.67ポイント、暗殺者の的中率が1.28ポイント高く、被ダメージが試合あたり0.40少なかった。どの判断機構が勝率差を作ったかを切り分ける実験は行っていない。また、やさしいの防御成功率は標準より高かった。成功率の分母は実際に有効な防御札を出した夜であり、防御札を出す頻度や防いだダメージ量とは異なる。各難易度の対戦相手も異なるため、この総合指標だけで防御判断の優劣は判断できない。

## 検証方法

- `Duel` の正式エンジンで開始から勝敗確定まで進めた。HP20、20枚、手札上限7枚、夜末補充、最大15夜と正式カード能力を使用。全てのデッキの投入上限および全提出の合法性を本番の検証関数で確認した。観測用のコピーはダメージ、襲撃、防御、暗殺者、回復を集計するフックを入れただけで、効果の分岐や値は同じ。6対戦それぞれで3シードを選び、観測用と加工していないエンジンで勝敗・決着夜・最終HP・提出枚数が一致した。
- やさしいと標準は `chooseEasyNpc` と `chooseNpc`、強いは `chooseStrongNpc`、最強はWeb Workerと同じ `chooseStrongestNpc(view, strongestRandom(seed))` を直接呼び出した。全方式とも双方が確定する前に選択し、最強にだけ本人の調査情報を渡した。相手の非公開状態だけを入れ替えた確認でも、判断に渡すビューと各方式の判断は同じだった。
- NPC同士を扱うためエンジンの両者入力モードで実行した。追加選択は、本番NPCと同じ評価関数・回収時の高評価優先／捨てる場合の低評価優先を両席に適用した。デッキ生成、エンジン、各方式の判断には分離した乱数を設定。本番の一部モードのようなゲーム処理と判断での乱数共有、UIの待機、Worker起動・通信、タイムアウト時の強いNPCへのフォールバックは再現していない。
- 各条件には144乱数ブロックを置いた。同一構成の条件は各ブロックで2シード分を生成し、同じデッキ構成を両者に渡し、各シードで席を交換して4試合。標準構成は固定。それ以外の構成は本番のデッキ生成器で抽選。独立ランダム・異種では各ブロックで2デッキを独立に抽選し、同じ2デッキとシードで難易度への割当と席をともに交換して4試合。独立抽選では偶然同じ構成になりうる。席交換や難易度間比較では意図的に同じデッキと乱数条件を再利用した。
- 勝率は勝ち数÷全試合、得点率は（勝ち数＋引き分け数×0.5）÷全試合。95%信頼区間は、同一ブロック内の席・デッキ割当・複数条件の相関を維持するため、ブロックごとの値を作って標準誤差を計算した正規近似。複数の相手をまとめる総合表でも、同じ番号のブロックをまとめた。直接対戦の得点率と50%を比較した。6分類均等集計は標準・ランダム・速攻・耐久・情報・異種に各1/6、ランダム内の2条件と異種内の3条件にも均等配分。各相手難易度も同じ重み。
- 「襲撃成功」は有効な襲撃値が発生した夜のうち、防御後に1以上通った割合。騎士の軽減を襲撃と特殊攻撃が共有する夜は、計測上は襲撃に先に割り当てた。「防御成功」は有効な狩人・罠師・騎士を出した夜のうち、それらが実際にダメージを防いだ割合。与・被ダメージは自傷や商人のコストを除く実HP減少、反撃を含む。同時に自傷でHP0になるときは対戦相手による減少を先に数えた。
- 暗殺者の的中率はエンジンが実際に判定した予想を分母とする。魔女実効率は実回復量÷（提出した魔女の枚数×4）。無効化、回復上限、回復前の決着もこの指標に反映する。1／2枚提出率の分母は手を選んだ夜。判断時間は並列Node実行中の選択関数の実測平均で、端末上の待ち時間の保証ではない。

## 再現方法

Node.js 22で実行。第2コマンドには第1コマンドのJSONLを渡す。

```powershell
node --disable-warning=ExperimentalWarning --experimental-strip-types scripts/npc-difficulty-winrates.mjs 144 > npc-difficulty-winrates.jsonl
node scripts/summarize-npc-difficulty-winrates.mjs npc-difficulty-winrates.jsonl
npm test
npm run build
```

既存の自動テスト139件と本番ビルドは成功。ビルドには既存のVercel Analytics由来の警告が1件あった。表には本試験だけを含め、観測フックの照合と動作確認用のミニ試験を除いた。
